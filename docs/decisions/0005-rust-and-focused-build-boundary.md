# 決策 0005：採用 Rust 並集中自研遊戲差異層

## 背景

Lattice Axiom 需要自行定義模組組合、無限體素世界、區塊生命週期、世界生成與持久化語義，但不需要以自行重造視窗、GPU 抽象、通用 ECS、網格化或序列化來證明這些假說。一人主導並由 AI 協作時，最大的風險不是單一功能寫不出來，而是同時維護過多非差異化基礎設施。

## 決策

1. 實作語言採 Rust，專案使用 Cargo workspace。
2. 自研範圍集中在主迴圈與順序排程、區塊與調色盤、登錄表、模組解析、世界生成、存檔語義，以及模擬到渲染的擷取邊界。
3. demo 直接採用成熟函式庫處理視窗與輸入、GPU 抽象、數學、ECS 儲存、體素網格化、噪聲、序列化、除錯 UI、Nickel 求值、動態函式庫載入與 RocksDB 存取。實作時再鎖定經測試的精確版本。
4. wgpu、RocksDB 等第三方系統必須藏在專案自己的窄介面後；「使用現成基礎設施」不等於讓其型別滲入所有內容模組。
5. 不以 Bevy、Godot 或其他完整引擎作為宿主。可以借鑑設計或在有明確限制時引入較小元件，但不繼承完整引擎的生命週期與升級節奏。
6. Rapier、glTF 與其他較重能力在垂直切片出現真實需求後再加入；demo 先使用 AABB、射線與純色方塊。
7. AI 適合實作有明確契約、狀態機、不變量與測試的小工作單元；產品語義、所有權、持久化邊界與驗收條件仍由專案維護者決定。
8. 使用開源專案時優先依賴並追蹤 upstream；若必須 fork，需有具體限制、授權檢查與回歸測試，不複製一套難以追蹤來源的大型子系統。

## 自研與採用邊界

| 領域 | demo 決策 |
| --- | --- |
| 遊戲核心與內容契約 | 自研 |
| 區塊、調色盤、流式生命週期 | 自研 |
| 套件宣告、解析與數值 ID | Nickel + 自研 Rust package kernel；見[決策 0010](0010-nickel-driven-package-system.md) |
| 動態原生載入 | libloading + 自研 ABI 驗證與註冊層 |
| 世界生成與產物記錄 | 自研 |
| 世界儲存語義 | 自研 `WorldStorage` 介面；RocksDB 實現 |
| GPU、視窗、數學 | wgpu、winit、glam |
| ECS 資料儲存 | hecs；排程保持簡單且由核心控制 |
| 體素網格與噪聲 | 自研 `latticeaxiom-voxel-mesh`（參考 block-mesh 演算法）與既有噪聲函式庫 |
| 序列化與除錯 UI | serde + bincode（置於自有 schema envelope）、egui |

## 結果

- 專案能把時間放在可組合世界平台的差異化問題上。
- Rust 的型別、測試與 Cargo 生態適合建立窄契約與 headless 驗證。
- 原生依賴、編譯時間與跨平台建置會成為持續成本，必須由 CI 及 crate 邊界控制。
- 不使用完整引擎意味著主迴圈、資源生命週期、工具整合與除錯體驗仍由專案負責。

## 被否決的方案

### 先完成通用遊戲引擎再做遊戲

它會讓渲染、編輯器、物理與資產工具先於玩家價值，無法快速驗證核心假說。

### 複製大型開源渲染器或引擎

短期看似取得控制權，長期卻失去 upstream 修正、來源追溯與可負擔的維護邊界。

### 以完整 Bevy 或 Godot 作宿主

它們適合其他產品目標，但會讓本專案的核心生命週期、模組邊界與渲染可替換性受宿主框架支配。

## 驗證

- workspace 的核心與內容 crate 不直接依賴 wgpu 或 RocksDB 型別。
- headless 測試不建立視窗或 GPU，也能走完整模擬與渲染擷取。
- 第一個垂直切片能行走、挖放方塊並跨重啟保存結果。
- 每次新增大型依賴時記錄它替代了哪項自研工作與對二進位、編譯時間的影響。
