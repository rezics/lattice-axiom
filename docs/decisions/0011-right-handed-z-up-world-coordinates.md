# 決策 0011：世界空間採用右手 Z-up 笛卡兒座標約定

## 背景

世界生成、區塊索引、物理、渲染、資產編譯、存檔與未來網路協定都會交換空間資料。如果各子系統分別假定不同的垂直軸、正方向或負座標取整規則，即使型別都寫成 `(x, y, z)`，仍會產生旋轉、鏡像、接縫、錯區塊和無法相容的持久資料。

「數學座標系」可以作為直觀說法，但不是足夠精確的技術定義：笛卡兒座標系可以選擇不同軸作為垂直軸，也可以採用不同手性。專案需要固定的是一組明確且可測試的座標、方向、單位與離散化約定，而不是依賴某個創作工具、交換格式或圖形後端的預設值。

## 決策

1. Lattice Axiom 的權威世界空間採用**右手笛卡兒座標系**，基底滿足 `+X × +Y = +Z`。
2. `+Z` 是上方，`XY` 是水平面。若需要世界方位名，`+X` 為東、`+Y` 為北、`-X` 為西、`-Y` 為南。
3. 座標與索引一律按 `(x, y, z)` 排列；高度或垂直區塊索引是 `z`，不得在核心 API、存檔鍵或內容契約中把 `y` 隱式解釋為高度。
4. 正旋轉遵循右手定則。繞 `+Z` 的正旋轉從 `+X` 轉向 `+Y`；從 `+Z` 朝原點俯視時為逆時針。
5. 權威世界長度單位是公尺，角度單位是弧度。第一版標準體素邊長為 `1 m`；編輯器和玩家介面可以顯示其他單位或角度制，但必須在邊界轉換。
6. 執行期實體的規範局部基底採用 `+X` 向右、`+Y` 向前、`+Z` 向上。沒有方向的物件不必製造「前方」語義；相機、燈光、骨骼或來源資產的特殊局部軸由相應契約和匯入器處理。
7. 創作格式和交換格式可以使用不同的手性、垂直軸、前向軸或單位。資產編譯階段必須讀取或宣告來源約定，並一次性轉換位置、方向、法線、切線、骨架、動畫、碰撞與語義插槽；執行期資產只使用規範基底。
8. 圖形 API 的裁剪空間、紋理座標和深度範圍屬於渲染後端約定。相機／渲染門面負責顯式轉換，不能反過來改變模擬世界的座標定義。
9. 座標約定屬於持久化與互通 ABI。存檔、lock 產物、生成記錄和未來網路訊息必須以 schema 版本保存明確的軸順序與單位，不能靠消費端猜測或按來源工具重新解釋。
10. 本決策只固定空間語義，不提前固定矩陣的行列儲存、變換乘法順序、世界位置的整數／浮點精度或浮動原點方案；這些實作選擇必須保持上述可觀察語義。

## 離散體素與負座標

整數體素座標 `(i, j, k)` 表示半開單元：

```text
[i, i + 1) × [j, j + 1) × [k, k + 1)
```

其中心為 `(i + 0.5, j + 0.5, k + 0.5)`。連續世界位置轉換為體素座標時，對每個分量使用向負無窮取整，而不是向零截斷。

設正區塊邊長為 `S`，方塊座標為 `b`，則每個軸都使用歐幾里得除法：

```text
chunk = b.div_euclid(S)
local = b.rem_euclid(S)    // 0 <= local < S
```

因此 `x = -1` 會進入 `chunk_x = -1` 的最後一個局部單元，不會錯誤落入 `chunk_x = 0`。三軸區塊鍵和範圍查詢都遵守同一規則。

## 邊界責任

```text
來源資產／交換格式
        │ 顯式基底與單位轉換
        ▼
規範執行期資產 ───────┐
                      │
右手 Z-up 模擬世界 ───┼──► RenderWorld ─► 後端裁剪空間
                      │        顯式轉換
權威區塊與存檔鍵 ──────┘
```

- 世界生成、物理、玩法和 `WorldStorage` 只看規範世界座標。
- 資產編譯器保留來源診斷，但輸出規範執行期基底。
- `latticeaxiom-render` 接收規範世界變換；具體後端負責投影與裁剪空間差異。
- 若未來提供其他遊戲或工具的相容層，軸交換只存在於轉接邊界，不能滲入核心資料模型。

## 結果

- 高度、二維地圖、三維密度場和區塊索引共享 `XY` 水平、`Z` 垂直的直觀關係。
- 世界生成、物理和創作工具之間減少反覆軸交換，但所有外部格式仍需透過明確轉換進入專案。
- 現有或未來採用不同約定的內容不能直接重新解釋數值；必須由版本化匯入器轉換。
- 單位、旋轉、負座標和體素邊界從一開始即可寫成跨子系統契約測試。

## 被否決的方案

### 採用 Y-up、XZ 水平面

這種約定本身仍是合法的笛卡兒座標約定，但會使本專案的二維規劃座標、三維高度表達和預定創作流程持續交換 `y`、`z` 語義，因此不作為核心世界約定。

### 直接沿用任一創作工具或交換格式

不同工具、資產類別和格式對垂直軸、前向軸、相機方向與單位的約定並不一致。把某個外部預設值當成未說明的引擎 ABI，會把偶然的工具行為固化進存檔與玩法。

### 由渲染後端定義世界空間

圖形 API 的裁剪空間是輸出邊界，不應決定世界生成、物理與持久化語義；否則更換後端或加入 headless 實現會改變核心資料解釋。

## 驗證

- 基底測試證明 `cross(+X, +Y) = +Z`，繞 `+Z` 的正四分之一轉把 `+X` 映射到 `+Y`。
- 對正負邊界值做 property test，證明 `b = chunk * S + local` 且 `0 <= local < S`。
- 世界位置、體素、區塊與局部座標的往返測試覆蓋 `-S-1`、`-S`、`-1`、`0`、`S-1`、`S` 和 `S+1`。
- 每種資產匯入器以非對稱測試模型驗證沒有鏡像，前、右、上方向與動畫、碰撞一致。
- headless 與 wgpu 實現消費相同 `RenderWorld`；後端轉換不能改變模擬位置、剔除結果或射線命中。
- 持久化 golden test 固定三軸順序、單位、負區塊鍵和 schema 版本。
