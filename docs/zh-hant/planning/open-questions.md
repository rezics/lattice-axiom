# 待決問題

這不是承諾清單，而是目前最容易被架構熱情掩蓋的不確定性。問題應透過討論、研究、原型或量測被關閉；真正形成重大選擇時，再建立決策紀錄。

## 優先級 0：先定義要做的遊戲

- [ ] 用一頁說清楚玩家、核心循環、情緒目標與最小可玩體驗。
- [ ] Lattice Axiom 是單一遊戲、創作平台，還是「官方遊戲 + 可組合平台」？
- [ ] 哪一項玩家價值必須依賴模組架構，而不只是工程上的優雅？
- [ ] 官方最小內容包需要哪些機制與內容才能驗證架構？
- [ ] 單機、合作、競技或大型多人，哪種網路模型屬於首要範圍？

## 優先級 0：定義模組契約

- [ ] 模組的最小單位、名稱、版本、能力與相依性如何表示？
- [ ] 宣告式組合語言要自訂，還是先用 TOML/JSON 與鎖定檔驗證概念？
- [ ] 發現、解析、註冊、啟用、停用與卸載各自的生命週期是什麼？
- [ ] 靜態、動態與 WASM 實現如何共用介面，又如何暴露不同限制？
- [ ] 模組衝突、能力提供者與可選相依性如何診斷？
- [ ] 信任政策由玩家、整合包作者、伺服器還是發行者決定？
- [ ] 儲存檔如何記錄已移除或升級模組所擁有的資料？

## 優先級 1：以量測確認「熱路徑消除模組邊界」

- [ ] 建立資料模組、原生模組與沙箱模組的同功能基準測試。
- [ ] 比較逐實體呼叫、批次查詢與編譯排程的成本。
- [ ] 定義可接受的 CPU、記憶體、載入時間與建置時間預算。
- [ ] 證明官方與第三方內容在進入同一執行表示後沒有額外來源成本。
- [ ] 量測 LTO 的實際收益，而不是假定靜態連結必然更快。

## 優先級 1：渲染邊界

- [ ] 渲染世界的最小資料模型與所有權是什麼？
- [ ] 渲染擷取是複製、雙緩衝、事件增量，還是其他方式？
- [ ] 普通材質、渲染功能與 Render Graph 擴充的權限邊界在哪裡？
- [ ] 自訂 shader 使用何種來源語言、中介表示、驗證與快取鍵？
- [ ] 動態模組第一次載入時，shader/pipeline 編譯的使用者體驗如何處理？
- [ ] 選哪兩個渲染候選做同一個垂直切片？

## 優先級 1：模型與物理資產規格

- [ ] glTF/GLB 是否能承擔主要交換格式，哪些資料必須使用 extension 或 sidecar？
- [ ] 第一版只支援哪些跨模型能力：注視、接觸點、裝備、受擊區或其他？
- [ ] 語義角色、能力、物理場與互動語義如何分層與版本化？
- [ ] Blender add-on 的最小功能是匯出、驗證，還是也包含物理預覽？
- [ ] 高解析度網格與低解析度 simulation cage 如何建立與對應？
- [ ] 局部形變的最小可信原型應採程序性位移、PBD 還是現成柔體 backend？
- [ ] 物理 LOD 在不同硬體上是否會影響命中判定或遊戲公平性？

## 優先級 1：多人與可重現性

- [ ] 客戶端與伺服器握手應比較哪些權威能力子圖、套件鎖定與 schema 狀態；哪些差異可由 adapter 或純表現政策接受？
- [ ] 客戶端與伺服器允許哪些純表現差異？
- [ ] 受擊與局部柔體同步輸入、狀態還是只同步玩法結果？
- [ ] 原生第三方模組如何進入伺服器，是否允許自動下載？
- [ ] 二進位快取、簽章、撤銷與供應鏈信任如何運作？

## 優先級 1：可組合世界生成

- [ ] 第一批兩個 `CaveTopologyProvider` 應選哪些受約束幾何圖、方向場或生長模型做對照？
- [ ] 地表與三維地下領地使用相同圖譜抽象，還是只共用所有權仲裁介面？
- [ ] 洞穴預算如何在主要拓撲、支洞、洞室、目的地與水文修正間換算？
- [ ] 地表群系、地下群系、深度帶與地質體如何共同影響淺層入口和深層洞穴？
- [ ] 跨規劃格與拓撲所有權域的入口契約需要保存哪些流體狀態，才能維持地下河與含水層連續？
- [ ] 第一個領地原型採用 Voronoi、冪圖、扭曲網格或其他候選中的哪兩種比較？
- [ ] Province、Region 與 Ecotope 的尺度、面積分布及形狀參數如何由實際旅行速度決定？
- [ ] `BiomePack` 世界份額由整合包、伺服器、玩家預設或內容作者中的誰治理？
- [ ] 哪些生成通道屬於第一版核心，且各自使用何種合成代數？
- [ ] `BoundaryProfile` 如何避免 `N²` 配對，同時處理海岸、峭壁、地下河與其他特殊接縫？
- [ ] 水文、岩層、侵蝕與大型結構要使用多大的規劃格及 halo 才能有界查詢？
- [ ] 產物生成記錄採多大的空間與語義粒度，才能兼顧局部失效、儲存成本、舊提供者封存與跨世代邊界？
- [ ] 洞穴原型用哪些拓撲與玩法指標判斷優劣，而不是只比較截圖？

## 優先級 2：生態與治理

- [ ] 模組 API 與資產 schema 的相容性承諾是什麼？
- [ ] 官方是否提供能力測試套件，確保 Vanilla 沒有使用私有捷徑？
- [ ] 授權中繼資料如何影響靜態連結、快取與再散布？
- [ ] 誰治理通用語義與擴充名稱，如何避免專案特例污染共通層？
- [ ] 文件、schema、範例資產與測試工具如何一起版本化？

## 建議的下一批文件

只有在相應問題開始有答案時才建立：

1. 一頁式遊戲體驗簡報。
2. 最小模組 manifest 草案。
3. `ResolvedModuleGraph` 資料模型草案。
4. 渲染擷取垂直切片測試計畫。
5. 一個帶骨架語義與腹部物理場的龍資產範例。
6. 下一份候選決策紀錄，例如「選擇原型用核心語言」；尚未決定前不預建空 ADR。
7. 二維多尺度領地與一千個合成群系的可重複原型。
8. 一個根域預設與兩個群系子域拓撲提供者、共享入口及三種形態的三維洞穴原型。
